# splitdev2 diagnosis

The defect is **key-only reuse of a CPU-worker registration across an autosplit rollback with a different expert slice**. There is no global runtime split boundary in the exchange algorithm. R1 changes the slice, but the worker keeps the previous slice's count, key order, native layer and arena descriptors.

## Evidence and exact index mechanism

`logs/boot.log:48-49` registers checkpoint layer 23 twice: `[190..288)` (N=98), then `[184..288)` (N=104). `base/exllamav3/model/moe_cpu_host.py:714-727` resolves both registrations through `by_key[layer_key]`, replaces only the device-side auxiliary tensors and returns the original worker index. Its immutable worker spec remains N=98. The CUDA log has no Python traceback, so it cannot formally identify a Torch call by itself.

The implicated Torch call is **`counts1.scatter_add_(0, shifted, torch.ones_like(shifted))`**, at `base/exllamav3/model/moe_cpu_host.py:1336` (fixed source: `src/exllamav3/model/moe_cpu_host.py:1369`). The index tensor is **`shifted`**, derived from that layer's **CPU-local `selected_experts`**, after dynamic map translation:

```python
# R1 layer 23 after rollback:
module.cpu_split_first = 184           # E=288, N=104
spec["num_experts"] = 98               # stale first registration
sel_cpu = physical_slot - 184          # or -1 for GPU picks
shifted = sel_cpu.reshape(-1) + 1      # sentinel -1 maps to bin 0
counts1 = torch.zeros(99, ...)
counts1.scatter_add_(0, shifted, torch.ones_like(shifted))
```

Physical slots 282..287 become CPU-local 98..103, then shifted indices **99..104**, outside **`[0,99)`**. The shared `ScatterGatherKernel.cu` error text does not distinguish a gather from this scatter. The AST-extracted **production registration and prefill methods** reproduce `scatter_add_: index 99 out of bounds for size 99` on the CPU harness. `out/tests-before.log` records that error; the fixed methods pass the same seam in `out/tests-after.log`.

The same stale count also reaches `smask1.index_select(0, shifted)` at `base/exllamav3/model/moe_cpu_host.py:1453` (a length-99 mask). More seriously, indices below 98 can silently compute the wrong expert: new local slot 0 should hold physical expert 184, but the original worker holds expert 190. For frequency-ranked placement these are the different experts at profile positions 184 and 190. The actual production exchange method reproduces this wrong promotion in the CPU harness. Resizing a histogram or clamping indices would conceal that corruption.

The brief describes a first-request failure, but the captured evidence is more precise: `logs/boot/docker-final.log:86-159` records successful short 41-token requests; line 160 starts a **5,590-token sparse warmup**, and line 163 starts the CUDA assertions. The streamed prefill path is size-dependent. Short decode can finish using the stale worker without exposing the histogram's bounds, which explains why load and short warmup are insufficient gates.

Live attribution remains **strongly supported, not GPU-proven here**: CUDA reports asynchronously and this workspace has no GPU or Torch. `probe-r1.py` / `Dockerfile.probe-r1` retain r1's bug and raise immediately before the original scatter, naming the layer, index tensor, size and range. Its CPU self-test produces `layer=L23 ... call=counts1.scatter_add_ index_tensor=shifted range=[0,104] size=99 cached_cpu=98` (`probe-selftest.log`). CHECK in the fixed image validates the corrected contracts and downstream gathers.

## Ranked hypotheses and outcomes

1. **Changed slice on rollback**: predicts the 98→104 retry preserves the old registration and fails prefill; confirmed at the real registration/scatter seam. Reverse 104→98 also uses wrong experts without necessarily exceeding bounds.
2. **Global exchange boundary/histogram**: predicts mixed-count layers fail even without rollback; falsified by code audit and production global-histogram sweep tests. Global scope allocates a *swap budget*, not a count or expert map.
3. **MTP_FAST sizes all experts from its first layer**: predicts layer 45's N changes every later layer's limits; falsified. Worker eligibility/layout require equal dimensions and top-k, while counts belong to native layers. Both 98/104 MTP placements pass the CPU tests.
4. **N=104 init stats encode local split indices**: predicts changing N produces an invalid permutation; falsified for the reader's supported format. It consumes full-E per-layer count vectors and slices their ranking separately for each module. The actual stats JSON is not supplied, so its full contents cannot be independently verified here; the reader and saved boot messages are the evidence.

## Fix and default compatibility

Modified five existing Python files and added `model/moe_split_check.py`. No changes to TabbyAPI, native code, quantized kernels, numerical accumulation, exchange transaction ordering or the shared-memory ABI. The complete patch includes r1.

With BY_DEVICE absent, the original key-only retry branch, split-layer bookkeeping and split resolution remain in use. CHECK defaults to off. The CPU differential test compares base/src registration specs, messages, IDs, live counts, auxiliary state, translation values and prefill result for the uniform path; they match. No claim of a measured GPU performance comparison is made. With BY_DEVICE set, registration identity follows the actual ordered CPU slice, and both prefill and decode now select the correct immutable native layer.

Retaining a rejected native registration is intentional: one extra CPU expert slice can remain in the pinned arena until shutdown for each changed-layout rollback. It adds load work/host memory, not a live routed layer. Its GPU aux/reconstruction caches are released. Recycling/replacing a native handle would require a new protocol and risk ack/descriptor misalignment; this Python-only append path uses the existing protocol. Record host memory on flan if repeated rollbacks become material. Every container restart resets the registry/arena.

## Debug mode and validation limits

`EXL3_MOE_CPU_SPLIT_CHECK=1` enables synchronous contract/range validation with `[SPLIT-CHECK] layer=... tensor=...` exceptions. It checks every split forward, worker count vs module first, ordered-list/aux/descriptor lengths, map permutations, router and translated IDs, exchange slots, the risky prefill scatter/mask gather, and batched pointer/scale/token gathers. Existing small local bound-class graph captures occur after the split submission checks; the checks are diagnostic readbacks, so reboot CHECK=0 before measuring throughput. No hidden request counter disables checks prematurely.

`python3 out/test_splitdev.py` runs 25 tests: **24 pass, one real-Torch CPU test skips** because Torch is not installed here. Base fails the regression (7 failures plus the scatter error). Tests execute production methods extracted by AST while replacing only device/worker I/O with bounded CPU vectors. They cover both rollback directions, changed profile order, append-only handle/ack identity, cache invalidation, no-override differential behavior, device override fallback/capping, layer-budget rollback, c1/c2/c3/c4 and prefill index ranges, production global histogram sweeps, actual exchange descriptor selection, MTP at either N, and named CHECK failures. `--torch` additionally verifies the invalid/valid histograms using actual CPU Torch; the Docker build runs all tests with that option.

Local validation additionally applies `diff -ruN base src` to a clean temporary base with zero fuzz, compares every resulting source byte with src, verifies both SHA manifests, compiles all changed Python files, checks the shell script, and self-tests the original-r1 probe. Results are in `validation.log`. Docker build, extension landing and the live GPU matrix are supplied in `OPERATOR.md` and have **not** run here. The unit reads/restores the current daily, starts at 98/104 with CHECK on, reboots CHECK off for the requested matrix, and gates 96/104 and 100/104 on the complete 98 result within the bounded slot.
