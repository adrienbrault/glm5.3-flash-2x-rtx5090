# MTP overhead: implementation and evidence

The overlay adds attribution and guarded exact transformations; it does **not** establish a new GPU speedup or demonstrate removal of 10 ms. No GPU, SSH, Docker or remote is available here. The measured baseline is R892: MTP-fast d1 N104 costs 27.06–27.74 ms/step, emits 1.72–1.74 tokens/step, and scores 62.6–63.9 tok/s. Plain N96 costs 16.3–17.2 ms. A matched plain **N104** control is still missing. Two different sequences at (2,1) costing 24.3 ms is neither a measurement nor a rigorous bound for causal recurrent verification at (1,2).

Read source references below relative to `src/`; the checksummed `base/` is the actual served-image snapshot, including exchange and MTP-fast. The overlay is Python only, with no extension ABI or quantization changes. All new optimization flags default off; depth-zero configuration is explicit opt-in. Existing component graphs keep their original defaults.

## What the supplied measurements discriminate

* R892 confirms the second CPU pool was a cause: joining the MTP layer to the trunk saves about 2 ms, already implemented by `EXL3_MTP_FAST=1` in this base.
* B2's pinned staging plus batched verification is neutral versus B1. Do not promise another multi-ms gain from these alone.
* R886 draft-all changes both acceptance and subsequent routing. Its 30.7 ms round versus exact 30.2 ms weakens the extra-CPU-picks hypothesis but does not isolate an individual verify phase; it also changes numerical outputs.
* R876's kernel/worker breakdown came from a different, CPU-heavy workload (3.63 CPU picks/layer), and its profiler added about 2.5 ms. Its multi-row pooled-indexer graph failure cannot be transferred to c1 MTP: this tree allows bsz1 q2 while pooled bsz>1 explicitly declines.
* `log-analysis.json` parses all supplied 64-job handoff windows. Medians of **window means**, not matched per-step timings: B0 gap/spin/compute = .142/.183/.364 ms, B1 = .075/.187/.348, B2 = .071/.187/.341. Mixed prefill/c1/c4, empty jobs and two unlabeled workers in B0 prevent summing these into a phase attribution. Neither gap nor spin is the exposed collect wait. The new event bracket around the actual done-flag wait settles that question.

`util/mtp_phase.py:38` records CUDA events on explicit/current streams and host `perf_counter_ns` timestamps. Normal steps query completed events and aggregate without a new synchronization. The final queue-drained flush synchronizes outstanding measurement events **only when profiling is enabled**, so it can emit a partial bucket. `EXL3_MTP_PHASE_STEPS` defaults to 64. Optional `EXL3_MTP_PHASE_TRACE=1` adds `MTP/…` record_function ranges for the diagnostic Kineto trace.

Profiling off performs no timestamps, event allocation, event queries, trace ranges, aggregation or log formatting during steps. Decorated methods become the original methods; explicit sites retain constant boolean guards. This is zero measurement work, not a claim of literally zero additional Python bytecode. Profiling on adds many events, especially per-layer worker waits: compare speed with it **off**, as R876 already shows observer cost. Only the serialized layer-split served path is instrumented in detail; TP rank streams are not attributed and GPU optimizations decline TP.

The decode timer also records `checkpoint_housekeeping` for recurrent boundary stashes/synchronizations before drafting.

CUDA envelope time includes queued kernels, stream waits and host submission gaps when the stream catches up. Host time measures enqueue/readback/bookkeeping, not kernel compute. Parent and child ranges overlap; GPU devices/side streams overlap. **Never add all reported numbers**. Read per-device forward spans plus worker-wait children, then use the trace to inspect the critical path. The whole-round host interval excludes completion of trailing asynchronous repair kernels; those can be charged to the next step's waits, while the GPU repair events still report their own execution. Startup, graph capture and page-boundary rounds should be analyzed separately; the summarizer skips the first bucket of each shape by default.

## Batch depth zero: implemented with cache safety

Base generator (`base/exllamav3/generator/generator.py:253`) and Tabby `DraftDepthRule` reject depth zero. The overlay accepts nonnegative MTP policy depths in `tabbyapi/common/config_models.py:510`, and `EXL3_MTP_MAX_BATCH=1` disables drafting whenever **active** jobs exceed one (including still-prefilling jobs). A configuration policy counts decode-ready jobs, matching its existing semantics.

Steady suspended rounds call ordinary target (B,1), no recurrent history, no exported MTP hidden, no draft forward or repair. Allocation/prompt initialization still exist; this cannot reclaim MTP VRAM or make every prompt-prefill operation free. Zero-depth suspension requires a recurrent target because non-recurrent partial-page reuse is outside this patch's cache proof.

Suspension is sticky for the affected jobs, including physical requeues. A c2→c1 shrink does **not** resume drafting on stale KV. A new, unrelated c1 job can draft normally. Whole target pages generated while suspended are tracked by content hash (`generator/job.py:677`); a future prompt referencing them also takes plain decode before MTP prefill can read stale draft entries (`job.py:1246`). Windowed draft slots from suspended jobs publish no reusable tags; suspended prefill also marks every full target-only prompt page; dirty hashes remain reachable across the CPU page tier and are pruned only after leaving both GPU and CPU caches. Persistent NVMe KV is rejected with batch suspension, because draft-validity metadata is process-local and cannot safely survive a restart. This conservative behavior is intentional; automatic catch-up requires retaining/replaying target hidden states, which contradicts zero MTP work during c4.

The cap is exact ordinary target decoding when it suppresses drafting. It is **not** a by-construction bit-identical comparison to always-on two-position MTP: changing target q_len from 2 to 1 can change floating-point numerics even at static placement, as already documented in the MTP-fast reference. Test the c4 cap against a same-N104 MTP-off plain control, and test all c1 schedule-only optimizations against the same MTP-enabled image with flags off. Do not claim the cap's output matches always-MTP before checking actual tokens.

## Decisive next probes

1. Profile N104 MTP and plain, identical static placement/prompt set. Split `verify.forward_device` and `*.cpu_worker_wait` from `draft.forward`, head/readback and repair. The delta can then be attributed without using c2 as a shape proxy.
2. Capture 32 warmed steps after 128 decode calls, separately below/above index_topk and spanning all position mod4 values. Inspect actual cudaGraphLaunch correlation IDs in MLA/KDA ranges, and any cudaStreamBeginCapture/cudaDeviceSynchronize in steady-state. A populated/configured slot alone does not settle replay.
3. Run repair merge probe at static placement for at least eight accepted steps; collect every mod4 and a page crossing (use a longer run if eight samples miss either). Any hidden or cache-byte mismatch rejects the merge. Equality on these samples permits further testing, not a general proof across contexts or layouts.
4. Run cap c1→c2→c1, dirty-prefix follow-up/requeue, then a new unrelated c1 job. There must be no draft/repair ranges for suspended jobs and no stale-cache read; compare cap sustained c4 to same-image N104 MTP-off. Scripts and the 60-minute arm plan are in OPERATOR.md.
