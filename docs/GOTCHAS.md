# Gotchas

**A cold prefill fails with `KeyError: 'dictionary is empty'` in `recurrent.py` `put()`.** GLM-5.3 has linear-attention (KDA) layers, so ExLlamaV3 builds a recurrent-state checkpoint cache even when TabbyAPI's `sysmem_recurrent_cache` is 0; the first checkpoint stash then finds a zero-size cache and pops from an empty dict. Decode does not stash, so short chats work and the first long prompt fails. Set `sysmem_recurrent_cache` above the size of one checkpoint (the launcher defaults to 1,024 MB). Seen in R858 on the first 8,192-token prefill.

**The chat template has no thinking switch.** `enable_thinking` is not read by GLM-5.3's template; the generation prompt always ends in `<think>`. `reasoning_effort` is the only control: the model's own template reads `low` and `high` and treats anything else, a missing value included, as `max`; the two templates the launcher serves treat a missing or unknown value as `high`.

**The fit estimate from tensor sizes is short by several GB.** In R858, 80 experts per layer on the CPU (estimated to fit 31 + 31 GiB) and 12 whole MoE layers on the CPU both filled both cards at module 45 of 50 and failed with `Insufficient VRAM in split for model and cache`; 104 experts per layer on the CPU booted with about 2 GB free on one card. Plan the ladder against a smaller budget than the load budget (`PLAN_SPLIT` in `scripts/r858-glm53-audition.sh`).

**Concurrency adds less aggregate throughput than on a GPU-resident model.** Four streams route to about four times as many distinct experts per layer, and the CPU side does not batch them: R858 measured 49.5 tok/s at c1 and 68.6 tok/s summed over four streams; the served configuration measured 65.3 at c1 and 87.7 summed over four streams with a different prompt per stream (R914).

**Tool calls arrive as plain text.** GLM-5.3 writes `<tool_call>NAME<arg_key>K</arg_key><arg_value>V</arg_value></tool_call>`; TabbyAPI passes it through as `content` unless the model config sets `tool_format: glm4_5`, whose parser reads that layout and returns `tool_calls` with `finish_reason: tool_calls`. Checked 2026-10-07, streamed and not streamed.

**Stock TabbyAPI ends a GLM tool-call turn when the reasoning quotes a think tag.** What it looks like: a `write_file` request whose body contains `</fake>` or `<think>x</think>` returns `finish_reason: stop`, no tool call, a short reasoning. What it is: the model writes `</think>` while planning how to escape the body, and the reasoning parser takes it as the end of reasoning. R868 measured it with the agent overlay's flags off; the overlay r2 (`docker/glm-agent-r2/`) returns the call.

**Literal GLM tags in a prompt are encoded as control ids, and the turn can end on them.** What it looks like: at temperature 0, a request that quotes `<|user|>`, `<|observation|>` or `</think>` (code under edit, logs, transcripts) stops early with `stop_str` `<|user|>` or `<|observation|>`, or returns a tool call with an altered body (R877, R880, overlay r2). What it is: TabbyAPI renders the message text into the template and encodes the result with added-token matching on, so a quoted tag becomes the control token itself. Refusing such prompts is not a fix: agent overlay r3 raised `ValueError: Tokenizer encoded a literal GLM tag as a control ID` on every one of them and generated nothing (R877). Revision 4 encodes message text as ordinary pieces (`docker/glm-agent-r4/`).

**`clear_thinking` decides whether an agent's next turn hits the prefix cache.** What it looks like: the first request after each new user message in an agent session prefills the whole previous tool loop again, although the client resends the same history. What it is: the model's template keeps an assistant turn's `reasoning_content` only when `clear_thinking` is defined and false, or for turns after the last user message. While a tool loop runs, its turns come after the last user message and keep their reasoning; once the next user message arrives they are before it, their reasoning is dropped from the rendered prompt, and the tokens differ from what the cache holds from that point on. The launcher's default `KEEP_THINKING=1` serves `scripts/templates/glm53-keep-thinking.jinja`, where an undefined `clear_thinking` counts as false (TensorFold's default, `THIRD_PARTY.md`); a request can still send `{"clear_thinking": true}` in `chat_template_kwargs`. R885c measured it with `scripts/glm53_keepthink_probe.py`: a follow-up request reused 7,680 of its 9,915 prompt tokens with the keep-thinking template and 0 with the model's own (`2026-10-08-r885c-glm53-combo-keepthink-015602`). TabbyAPI `53da7919` returns an empty `usage` on non-streamed chat completions, so the probe streams with `include_usage` (R885b read no token counts).

**The legacy Docker builder rewrites `.dockerignore` when `-f` points outside the build context.** What it looks like: an overlay build fails at its first step, `sha256sum -c SHA256SUMS`, with a mismatch on `.dockerignore`, although the package on disk is intact. What it is: with the Dockerfile outside the context, the legacy builder writes its own `.dockerignore` into the context it sends, and the overlay's checksum gate covers that file. Copy the Dockerfile into the context and pass `-f` with a path inside it (R882, `docker/glm-agent-r2-on-cheapswap-r3/README.md`).

**The GPU lock gives no queue order.** What it looks like: units queued one after another on `/srv/qwen5090/gpu-exclusive.lock` may take the GPUs in a different order than they were queued; the driver's `queued behind:` line lists the other registered units, not a position. What it is: `flock(2)` wakes waiters in no defined order. A unit that must run after specific others has to wait for them by name: R885's driver waits until the R883 unit is inactive before it queues, so R883's restore step cannot replace the configuration R885 serves.

**A parked CPU worker pool costs about 210 µs to wake.** What it looks like: the first CPU expert job after an idle gap (the first token after a prefill, the first request after a pause) takes about 518 µs instead of about 300 µs. What it is: between jobs the worker threads park, and waking them costs time; R874c measured 518 µs per job with 2 ms gaps against 304 µs with spinning, and no difference at the 100 µs gaps of steady decode.

**Two hardware threads per core halve the CPU expert rate.** 16 worker threads on the 8-core 9800X3D measured 20.2 tok/s at c1 against 46.2 with 8 (R860); 8 threads on the SMT siblings read 50.5 GB/s against 61.4 GB/s on the physical cores (R874). Confining the whole TabbyAPI process to one core to keep it off the worker's cores costs 31 % (R871).

**The first requests after a boot decode slowly.** What it looks like: a 4,089-token request decodes at 21.7 tok/s and a 131,089-token request later in the same boot at 48.7 (R870); with static placement the first 4k request runs at 42.4 and the next one at 60.8 (R872). What it is: the placement holds the experts of the traffic it was fitted on or has adapted to, and the first prompts after a boot (and the random word-list filler of the depth probes) route elsewhere. Warm a boot with the kind of content being measured before reading decode at depth.

**One c1 sample does not separate a change from noise.** Boot-to-boot drift of the c1 score on one configuration measured 1.3 % (R864, A against A2), 0.6 % (R866), 1.7 % (R871, t8 against t8b) and 0.9 % (R872, SB against SB2); the R882b configuration read 59.9 in R882b and 61.1 in R883's control; the served configuration without its four host-side MTP flags read 65.4 and 64.2 in two arms of one R914 session. A single code run in R860's serving boot read 38.5 tok/s against 45.4 in the arm before it with the same configuration. Compare arms in one session with a repeated control and two runs per kind.

**Faster sweeps of the stock dynamic placement cost more than they save.** Sweeping every 64 tokens at floor 4 instead of every 128 at floor 8 lowered the simulated CPU share from 0.345 to 0.288 and measured 39.1 against 48.9 tok/s (R866): each swap rereads two experts from the checkpoint during an all-device sync, and a sweep four intervals overdue runs inline, mid-generation. The exchange mode of `docker/cheapswap-r3/` copies between the pinned arena and the GPU instead (0.46 ms per pair, R872).

**MTP depth 2 and 3 do not fit next to 96 to 104 CPU experts per layer at a 256k cache.** They fail with `Insufficient VRAM` (R860, R867); depth 1 needs 100 or more experts per layer on the CPU at half the batch, or 104 at the base settings. Each verify row routes to its own experts, so at c1 a step with a draft reads close to twice the CPU expert bytes.

**The edit probe's prompt is the probe's own helper code.** `glm53_probe.py`'s `edit` kind asks for a rewrite of `glm53_verify.py`, `r860_score.py`, `glm53_resources.py` and `glm53_follow.py`. A change to one of those files changes the prompt, so edit rates are comparable only between runs of the same scripts.

**Small solid-colour images are a weak vision check.** The 64-pixel red and blue squares (about 43 prompt tokens) were answered `White` or `Teal` for blue on configurations that passed the 256-pixel check (R866, R867, R869, R871, R872). The check in `glm53_probe.py --phase vision` now uses 256-pixel images with red, blue, green and a left/right split.

**Placement checks need the dynamic split registrations.** With `CPU_SWAP=0` the engine registers no dynamic CPU split, and the launcher's offload check (`glm53_verify.py`) rejects the boot (R860's `predict` arm). Trace and profile with placement on, or with `PLACEMENT=static`, which the check accepts.

**One prompt in every stream overstates the concurrency figures.** What it looks like: a 4-stream sum measured with the same prompt in every stream reads higher than the same configuration under mixed traffic. What it is: streams writing the same text route to mostly the same experts, so the CPU worker reads fewer distinct experts per step. R899 (`2026-10-08-r899-glm53-c4-distinct-061545`) measured 104.8 tok/s summed at c4 with one prompt against 95.7 with a different prompt per stream, and 78.1 against 79.0 at c2. `glm53_probe.py --distinct` gives each stream a different prompt; every concurrency figure from R911 on uses it.

**Greedy output is not reproducible from one run to the next.** What it looks like: the same temperature-0 request returns text that diverges after a few to a few hundred characters when repeated. R892 and R894 saw it across boots with exchange swaps and with static placement; R910b (`2026-10-08-r910b-glm53-determinism-092105`, static placement, MTP off) repeated five requests in the same process and four of the five diverged, at characters 19 to 525. Teacher-forced logits are identical within one process (R893), so the variation is in the generation path. Exactness checks that compare two runs cannot be read until its source is fixed; `docs/PLAN.md` lists that work.
